                                                4.1.2
    ловим deadlock. по шагам:
    1): foo(baz) захватывает lock, идёт исполнять baz.
    2): начал исполнять baz, который создаёт, запускает и ожидает(!!) поток t. 
        то есть вся программа ожидает, пока t выполнит свою работу.
    3): поток t запускает foo(bar), где пытается захватить lock. у него это не получается, 
        т.к. lock захвачен в 1), поэтому ждёт, пока освободится lock. deadlock
<br>

                                                4.1.3
    эта программа выполнится корректно, если Random.nextInt(0, 100_000) выдаст 0. иначе -- deadlock.
    1): пусть Random.nextInt(0, 100_000) == c != 0. тогда запустится foo(lock, c), захватывает lock, 
        вызывает и ожидает foo(lock, c - 1).
    2): исполняется foo(lock, c - 1), пытается захватить lock, не получается, т.к. lock захвачен в 1), и ожидает, 
        пока отпустят lock. deadlock 
<br>

                                                4.1.4
    зависит от потребности разработчика:
    1): если считать, что get должен возвращать самое последнее число, тогда рассмотрим такой сценарий:
        1.1): допустим, есть два потока: А и В. пусть мы в сумме инкерментировали 10 раз(х == 10), далее:
        1.2): пусть А в этот момент вызвал get(). смотрим на строчку h.data = increment(0);
              increment(0) вернул 10, но мы не успели записать в h.data и случился context switch. 
        1.3): поток В инкрементировал ещё 5 раз, после чего context switch.
        1.4): исполнение вернулось к потоку А: h.data = 10; return h.data; 
        1.5): верули 10, хотя по условию 1) должно было вернуться 15.
        
        то есть это не потокобезопасная программа.

    2): если же для разработчика поведение, описанное в пунктах с 1.1) по 1.4) считается валидным, 
        то тогда программа считается потокобезопасной.


    данный код не имеет data races по отношению к Holder.data, т.к. в каждом get создаётся свой Holder.
